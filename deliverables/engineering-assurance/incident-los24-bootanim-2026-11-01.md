## 4. 根因分析（5 Why，针对主候选）

| 层 | 追问 | 答案 | 证据等级 |
|---|---|---|---|
| W1 | 动画为什么永不停？ | `service.bootanim.exit` 从未置 1，即 `bootFinished()` 从未被调用 | 证实（源码 + 逐帧推进观测） |
| W2 | `bootFinished()` 为什么没被调用？ | system_server 未启动，或起来后反复死亡 | 推断（报告 1.4 自述为条件命题） |
| W3 | system_server 为什么起不来？ | 未拿到可用的 `/data`，或依赖的 HAL/服务不可用 | 推断 |
| W4 | `/data` 为什么不可用？ | `on nonencrypted` 未触发，vold 未完成解密 | 推断；报告原表述有误（见 7.1 #2） |
| W5 | 为什么解密失败？ | ① `/metadata` 密钥容器已被 `-w` 抹除（密文孤儿化）；② key blob 跨版本 version binding 失效；③ LOS 侧 fstab/vold 的失败处置与重建路径有缺口 | ①机制确定、动态待验；②推断且触发条件未核对；③新候选，离线可查 |

**5 Why 的局限（必须写进结论）**：

1. W2 起全为推断。静态分析只能证明「相容」（不与「动画在播」矛盾），不能证明「因果」。
2. 5 Why 假设单一线性链，而本现场至少三类机制并存且互相掩盖：若 `/metadata` 已毁，「version binding 失效」永远无法被证伪——它已不是第一道失败点。
3. W5① 把事故性质从「技术不兼容」改成「操作事故」：前者改设备树，后者须先承认数据已丢、重建干净基线。
4. 一条报告没做的反向推论：那次 `-w` 毁掉 metadata 之后，**原厂 A17 仍能正常启动**（§31 记录首次启动 3 分 20 秒），说明存在一条「把这块 /data 重新初始化起来」的路径且原厂走通了。若 LOS 走不通，差异在 LOS 侧——fstab 的 `check`/`formattable` 组合、vold 的失败处置、apexd 对 `/data/apex` 的处理——而不在「密钥状态」本身。

## 5. 预防措施

**针对「零日志现场」**

- 流程：任何「无法观测」的故障，先投 30 分钟建立通道（adb / TWRP / pstore / UART），通道不通不得继续推理。反例：本次在无通道状态下做了 5 章静态分析。
- 流程（本次最痛的一条）：**先取证、后恢复**。`restore_stock_full.sh` 一把刷回，把 `/data`、`/metadata`、pstore 推进到新状态，原故障态证据随之永久消失。恢复动作必须排在只读快照之后。
- 时效：dropbox 默认只保留 3 天，watchdog / system_server_crash 记录 3 天后自动蒸发；ramoops 无 ECC 时冷复位即丢。取证窗口是「最后一次复现后 3 天内」且「禁止长按电源，一律 `fastboot reboot` 收尾」。
- 工具：刷机脚本 `set -euo pipefail` + `tee`，并**校验关键命令的输出内容而非退出码**；`-w` 之后必须读回分区状态验证。构建期打开 `CONFIG_PSTORE_RAM` 并实测可读，作为启动镜像验收项。

**针对「跨大版本移植」**

- 流程：设备树与 blobs 同源（A17 blobs 配 A17 设备树），建版本矩阵门禁；跨大版本把「format data + erase metadata」列为硬性前置，并在脚本里验证它真的发生。
- 文档：把「不 wipe 直接接管加密 /data」列为禁止操作，附本次不可逆后果。

**针对「结论未定案就往下走」**

- 流程：基线冻结——每份报告开头须有《已证实事实清单》，条目冲突时先解决冲突再分析；每个「排除」须写明依赖的前提、验证方式与验证时间。
- 流程：排除项设 24 小时有效期，超期未复验即重验（本次 `-w` 的排除依据从 10-27 沿用到 11-01，从未复验）。
- 文档：结论强制带（证实）/（推断）/（待验证）标签；未定案时标题不得用「根因定位」；**继承来的「已排除」必须回源，不得直接引用**。

### 7.2 `fastboot -w` 假成功（P0 级证据）

`flash-log-1458.txt:42-47`、`flash-log-1609.txt:46-51`、`flash-log-v32-1809.txt:46-51` 三处一致：

```
== 清空 userdata（fastboot -w）==
  Erasing 'metadata'                                 OKAY [  4.020s]
  Erase successful, but not automatically formatting.
  File system type raw not supported.
  Finished. Total time: 5.492s
  ✓ userdata 已清空
```

判读：

- （证实）userdata 的擦除/格式化没有任何证据行；`/metadata` 确实被抹除——这三次有日志的刷机，日志里直接打了 `Erasing 'metadata'`。
- （证实）三份日志收尾的验证段均写「`ro.build.version.release` 期望 16」，说明这三次刷的是 A16 blobs 构建，正对应 §27 那次「卡在开机动画」——即「清 data 后仍卡住」所在的实验，其 `-w` 是假成功。
- （待验证）`fastboot -w` 是否**必然**擦 metadata 并无 AOSP 层保证：`fastboot.cpp` 的 `-w` 只置 `wants_wipe` 标志，实际擦哪个分区由该设备构建产出的 `fastboot-info.txt` 里的 `if-wipe` 指令决定。本地产物与 OTA zip 中均未见该文件，故 §31 那次无日志的 `-w` 到底擦了哪些分区，仍未定。上面三次是日志直证，不受此影响。
- （推断）`/metadata` 是元数据加密的密钥容器所在分区。抹掉它而保留 userdata 密文，`/data` 即进入「密钥已毁、密文尚存」的**密文孤儿化**状态——这是本报告没有的**机制 C**，与 version binding（机制 B）和 ROOT_OF_TRUST（机制 A）都不同。它必然解不开，但成因是自伤。
- 反向推论：此后原厂 A17 仍能正常启动（§31），说明存在「重新初始化这块 /data」的可行路径；若 LOS 走不通，差异在 LOS 侧（fstab 的 `check`/`formattable`、vold 的失败处置、apexd 对 `/data/apex` 的处理），这一支离线可查。
- **E1b 不是待做实验**：E1b 定义为「`erase metadata` + `-w`」，而 `-w` 在本环境下的实际行为就是 `erase metadata`——两个成分已被同一次操作覆盖，不可逆后果已部分实现。把它当「尚未执行的实验」会重复支付一次不可逆成本。
